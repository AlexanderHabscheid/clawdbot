# Centris AI — Agent Guidelines

Read this before planning or writing any code.

## Centris Philosophy

**For users:** Download the app and immediately control your entire computer with your voice — no setup, no configuration, no technical knowledge required.

**For developers:** The SDK and CLI exist to build connectors that make Centris faster and more capable — extending what voice commands can do across apps and services.

**The invisible system:** Users never see the backend, the connectors, or the infrastructure — they just speak and things happen.

Everything we build serves these three principles. If a change adds friction for the user, it's wrong.

## Architecture — What Makes Centris Specific

Centris is an overlay on top of the OpenClaw codebase. The base repo handles CLI, messaging channels, and general agent infrastructure. Centris adds:

### 1. Chrome Extension Bridge (`src/gateway/centris-extension-bridge.ts`)
- WebSocket connection at `/ws/centris/extension` between the gateway and the user's real Chrome browser.
- Single extension connection (replaces old on reconnect). 30s command timeout. 20s server-side ping keeps MV3 service workers alive.
- Command/response protocol: gateway sends `{ type, id, data }`, extension responds `{ type: "response", id, success, data }`.
- The bridge is the **only** path to the browser. No Playwright. No puppeteer. No screenshots. Real cookies, real sessions, real user accounts.

### 2. Chrome Extension (`extension/`)
- MV3 service worker architecture. Modules loaded via `importScripts` in dependency order.
- Key modules: `snapshot.js` (DOM snapshot extraction), `interactions.js` (click/type/scroll — strict mode, no fuzzy fallbacks), `websocket.js` (connection + reconnection), `connection_manager.js` (lifecycle), `config.js` (local-first gateway discovery, production fallback).
- Connects to local gateway first (ports 18789, 19001), falls back to production Railway gateway.
- Snapshot pipeline: ARIA role filtering → visibility filtering → size filtering → instruction-aware keyword scoring → maxChars limiting.

### 3. Domain Router (`src/agents/centris-router.ts`)
- Zero-LLM-cost keyword router. Classifies user messages into domains: `browser`, `computer`, `file`, `general`.
- Each domain gets only its relevant tools (e.g., browser domain → `centris_browser`, `web_search`, `web_fetch`, `tts`).
- Weighted keywords resolve ambiguity (e.g., "slack app" → computer, "slack" → browser).
- Ties fall back to `general` (all tools available).

### 4. Modular System Prompts (`src/agents/centris-prompts.ts`)
- ~2,000-2,400 token budget (vs ~6,800 for full OpenClaw prompt).
- Domain-specific instruction blocks injected based on router classification.
- Cherry-picks only Safety, Tool Call Style, Skills, and Runtime from OpenClaw — no massive workspace context.

### 5. Browser Tool (`src/agents/tools/centris-browser-tool.ts`)
- 8 actions: `snapshot`, `click`, `type`, `navigate`, `scroll`, `press_key`, `tabs`, `read_page`.
- **Auto-batching:** `navigate` returns interactive elements AND `click` returns post-click elements + page content. This collapses 7-turn flows into 3 turns.
- **Landmark filtering:** uses ARIA landmarks (`<main>`, `<nav>`, `role="main"`) to separate content from chrome. Position heuristic fallback (x < 200px = sidebar). No site-specific hardcoding.
- **Token efficiency:** strips `_internalNodes`, `bounds`, `stableHash` from LLM output (~45% reduction). Elements slim to `{id, t, n}`. 4000-char cap on snapshots and page content.

### 6. Desktop Control Tool (`src/agents/tools/centris-computer-tool.ts`)
- Native Accessibility API control — exact coordinates, <10ms, no screenshots.
- 18 actions: snapshot, click_element, type_into_element, press_key, find_elements, list_apps, launch_app, activate_app, list_windows, focus_window, move_window, resize_window, mouse_click, mouse_move, type_text, key_combo, scroll, get_displays.

### 7. Context Pruning (`centris-router.ts` — `compactStaleSnapshots`)
- Centris is voice-first: each command is independent. Old conversation history is cleared before each new command.
- Prevents token growth (3K→7K→9K→22K) from accumulated stale turns and old nodeIds.

### 8. Web Memory — Injected Context (Never Skip the LLM)
- **The system can never skip the LLM.** Every command goes through the agent. There is no "instant" or "cache-only" execution path that bypasses the model.
- Web memory is used as **injected context** to reduce LLM calls and make the agent loop faster and cheaper. When we have a cached route for (url, intent), we inject it into the agent's context so it knows what to click before getting to the website, app, or webpage.
- Flow: resolve web memory (url + intent from command) → if hit, inject cached route/actions into agent prompt → agent runs with this context → fewer tool calls, faster completion. If miss, agent runs normally.
- Clients pass `url` in context when they have a browser tab; optionally `userId` when authenticated for per-user Supabase storage.

## Engineering Preferences

These apply to all planning and code changes:

- **DRY is important** — flag repetition aggressively.
- **Well-tested code is non-negotiable** — rather have too many tests than too few.
- **"Engineered enough"** — not under-engineered (fragile, hacky) and not over-engineered (premature abstraction, unnecessary complexity).
- **Handle more edge cases, not fewer** — thoughtfulness over speed.
- **Explicit over clever.**
- **Token efficiency matters** — every byte sent to the LLM costs money and latency. Never send data the model doesn't need.

## Plan Mode Review Process

When in plan mode, work through these sections interactively. For each issue found:

1. Describe the problem concretely with file and line references.
2. Present 2-3 options (including "do nothing" where reasonable).
3. For each option: implementation effort, risk, impact on other code, maintenance burden.
4. Give an opinionated recommendation mapped to the preferences above.
5. Ask whether to proceed before implementing.

### Review Sections

**1. Architecture** — system design, component boundaries, coupling, data flow, scaling, security.

**2. Code Quality** — organization, DRY violations, error handling gaps, edge cases, tech debt, over/under-engineering.

**3. Tests** — coverage gaps, assertion strength, missing edge cases, untested failure modes.

**4. Performance** — N+1 queries, memory concerns, caching opportunities, slow code paths, token waste.

### Workflow

Before starting, ask:

- **BIG CHANGE** — work through interactively, one section at a time, max 4 issues per section.
- **SMALL CHANGE** — one question per review section.

Number issues, give letters for options. Recommended option always first.

## Key Token Efficiency Rules

1. Never send `_internalNodes`, `bounds`, `stableHash`, or extension metadata to the LLM.
2. Cap all content at 4000 chars (~1K tokens). Be consistent across all actions.
3. Auto-batch: `navigate` and `click` must include their results — never force extra round-trips.
4. Strip duplicate fields (`text` vs `content`, `id` vs `nodeId`).
5. Compact stale context before every new command.
6. The router should narrow tools to only the relevant domain — fewer tools = fewer tokens in tool schemas.

## Testing Browser Changes

- Unit tests: colocated `*.test.ts` files. Mock the extension bridge.
- Live tests: require the Chrome extension connected to a running gateway. Use `LIVE=1 pnpm test:live`.
- Manual testing: navigate to a real site, verify element counts, verify landmark filtering, verify click auto-includes page content.
- Always verify: turn count (should be 3 for navigate→click→respond), token usage (check snapshot char counts), and that stale nodeIds are never reused.
